# Approval Chains

Approval chains add multi-step approval workflows to HITL.sh requests. They're designed for enterprise organizations that need structured sign-off processes — for example, requiring both a team lead and a compliance officer to approve before a decision is finalized.

<Note>
Approval chains are available on the **Enterprise** plan. Organizations on the Business plan can upgrade to access this feature.
</Note>

## How Approval Chains Work

An approval chain is a sequence of steps attached to a request. Each step has one or more designated approvers who must submit a decision (approve or reject) before the chain progresses.

<Steps>
<Step title="Create Request">
Create a request in a loop as usual via the API.
</Step>

<Step title="Attach Approval Chain">
Create an approval chain for the request, specifying the mode, steps, and approvers.
</Step>

<Step title="Approvers Decide">
Each approver reviews the request and submits their decision with an optional comment.
</Step>

<Step title="Chain Resolves">
Once all steps are resolved, the chain status updates to `approved` or `rejected`.
</Step>
</Steps>

## Approval Modes

Approval chains support two modes that control how steps are evaluated:

<CardGroup cols={2}>
<Card title="Sequential" icon="arrow-right">
Steps are evaluated in order. Step 2 only becomes active after Step 1 is approved. If any step is rejected, the chain is rejected.
</Card>

<Card title="Parallel" icon="arrows-split-up-and-left">
All steps are active simultaneously. Approvers in any step can submit decisions at any time. The chain resolves when all steps complete.
</Card>
</CardGroup>

### When to Use Each Mode

| Mode | Best For | Example |
|------|----------|---------|
| `sequential` | Hierarchical sign-off where earlier approvals inform later ones | Team lead approves, then compliance officer reviews |
| `parallel` | Independent reviews where order doesn't matter | Legal, finance, and engineering each review independently |

## Chain Statuses

Both chains and individual steps use the same status values:

| Status | Description |
|--------|-------------|
| `pending` | Waiting for approver decisions |
| `approved` | All required approvals received |
| `rejected` | At least one approver rejected |
| `skipped` | Step was skipped (e.g., earlier step in sequential chain was rejected) |

## Step Configuration

Each step in a chain has:

<ParamField body="step_order" type="integer" required>
The position of this step in the chain (starting from 1). In sequential mode, steps are evaluated in this order.
</ParamField>

<ParamField body="approver_ids" type="array" required>
Array of user IDs who are authorized to submit decisions for this step. At least one approver is required.
</ParamField>

<ParamField body="require_all" type="boolean" optional default="false">
When `true`, **all** approvers in `approver_ids` must approve for the step to pass. When `false`, **any single** approval is sufficient.
</ParamField>

## API Reference

### Create an Approval Chain

Attach an approval chain to an existing request.

```
POST /v1/requests/{requestId}/approval-chain
```

<CodeGroup>

```python Python
import requests

chain_data = {
    "org_id": "64a1b2c3d4e5f6a7b8c9d0e1",
    "mode": "sequential",
    "steps": [
        {
            "step_order": 1,
            "approver_ids": ["65b2c3d4e5f6a7b8c9d0e1f2"],
            "require_all": False
        },
        {
            "step_order": 2,
            "approver_ids": [
                "66c3d4e5f6a7b8c9d0e1f2a3",
                "67d4e5f6a7b8c9d0e1f2a3b4"
            ],
            "require_all": True
        }
    ]
}

response = requests.post(
    f"https://dev.api.hitl.sh/v1/requests/{request_id}/approval-chain",
    headers={"Authorization": f"Bearer {api_key}"},
    json=chain_data
)
```

### Get Approval Chain

Retrieve the current state of an approval chain for a request.

```
GET /v1/requests/{requestId}/approval-chain
```

<CodeGroup>

```python Python
response = requests.get(
    f"https://dev.api.hitl.sh/v1/requests/{request_id}/approval-chain",
    headers={"Authorization": f"Bearer {api_key}"}
)

chain = response.json()["data"]["approval_chain"]
print(f"Chain status: {chain['status']}")
for step in chain["steps"]:
    print(f"  Step {step['step_order']}: {step['status']} ({len(step['decisions'])} decisions)")
```

```javascript Node.js
const response = await axios.get(
    `https://dev.api.hitl.sh/v1/requests/${requestId}/approval-chain`,
    { headers: { Authorization: `Bearer ${apiKey}` }}
);

const chain = response.data.data.approval_chain;
console.log(`Chain status: ${chain.status}`);
chain.steps.forEach(step => {
    console.log(`  Step ${step.step_order}: ${step.status} (${step.decisions.length} decisions)`);
});
```

```bash cURL
curl https://dev.api.hitl.sh/v1/requests/{request_id}/approval-chain \
  -H "Authorization: Bearer your_api_key"
```

</CodeGroup>

### Submit a Decision

Submit an approve or reject decision for a specific step in the chain.

```
POST /v1/approval-chains/{chainId}/decide
```

<ParamField body="step_order" type="integer" required>
The step number to submit a decision for
</ParamField>

<ParamField body="decision" type="string" required>
Either `"approve"` or `"reject"`
</ParamField>

<ParamField body="comment" type="string" optional>
Optional comment explaining the decision
</ParamField>

<CodeGroup>

```python Python
decision_data = {
    "step_order": 1,
    "decision": "approve",
    "comment": "Content meets quality standards. Approved for next review."
}

response = requests.post(
    f"https://dev.api.hitl.sh/v1/approval-chains/{chain_id}/decide",
    headers={"Authorization": f"Bearer {api_key}"},
    json=decision_data
)
```

```javascript Node.js
const decisionData = {
    step_order: 1,
    decision: "approve",
    comment: "Content meets quality standards. Approved for next review."
};

const response = await axios.post(
    `https://dev.api.hitl.sh/v1/approval-chains/${chainId}/decide`,
    decisionData,
    { headers: { Authorization: `Bearer ${apiKey}` }}
);
```

```bash cURL
curl -X POST https://dev.api.hitl.sh/v1/approval-chains/{chain_id}/decide \
```

## Error Handling

The approval chain API returns specific errors for common scenarios:

| Error | Status | Description |
|-------|--------|-------------|
| Approval chain already exists | `409 Conflict` | A chain already exists for this request |
| Approval chain not found | `404 Not Found` | No chain exists for the given request |
| Chain is no longer pending | `400 Bad Request` | The chain has already been resolved |
| Step is no longer pending | `400 Bad Request` | The step has already been resolved |
| Not an approver | `403 Forbidden` | The authenticated user is not in the step's approver list |
| Already decided | `409 Conflict` | The user has already submitted a decision for this step |

## Use Case Examples

### Sequential: Content Publishing Pipeline

A two-step approval where the editor reviews first, then the compliance team signs off:

```python
# Step 1: Editor reviews content quality
# Step 2: Compliance team verifies regulatory requirements (both must approve)
chain_data = {
    "org_id": org_id,
    "mode": "sequential",
    "steps": [
        {
            "step_order": 1,
            "approver_ids": [editor_id],
            "require_all": False
        },
        {
            "step_order": 2,
            "approver_ids": [compliance_lead_id, compliance_backup_id],
            "require_all": True
        }
    ]
}
```

### Parallel: Cross-Functional Review

Three departments review independently — all must approve:

```python
# Legal, finance, and engineering review in parallel
chain_data = {
    "org_id": org_id,
    "mode": "parallel",
    "steps": [
        {
            "step_order": 1,
            "approver_ids": [legal_counsel_id],
            "require_all": False
        },
        {
            "step_order": 2,
            "approver_ids": [finance_director_id],
            "require_all": False
        },
        {
            "step_order": 3,
            "approver_ids": [engineering_lead_id, cto_id],
            "require_all": False
        }
    ]
}
```

## Best Practices

<AccordionGroup>
<Accordion title="Keep Chains Short">
Limit chains to 2-3 steps. Longer chains slow down resolution and increase the chance of bottlenecks. If you need more steps, consider whether some reviews can happen in parallel.
</Accordion>

<Accordion title="Use require_all Sparingly">
Only set `require_all: true` when every approver's sign-off is genuinely required (e.g., compliance scenarios). For most steps, a single approval is sufficient and faster.
</Accordion>

<Accordion title="Choose the Right Mode">
Use **sequential** when earlier steps inform later ones (e.g., technical review before legal review). Use **parallel** when reviews are independent and order doesn't matter.
</Accordion>

<Accordion title="Include Backup Approvers">
Add multiple approver IDs to each step so that the chain doesn't stall if one approver is unavailable. With `require_all: false`, any one of them can unblock the step.
</Accordion>

<Accordion title="Monitor Chain Status">
Poll the chain status or use webhooks to detect when chains are resolved. Stale pending chains may indicate an approver bottleneck.
</Accordion>
</AccordionGroup>
